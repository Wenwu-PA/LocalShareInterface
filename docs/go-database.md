# SQLite: ограничения и восстановление

`database.max_mb` в `config.go.yaml` ограничивает основную БД; по умолчанию
512 МиБ, допустимо 16–16384 МиБ. Перезапустите сервер после изменения.

Лимит реализован через SQLite `max_page_count` с учётом размера страниц существующей
БД. Он задаётся для каждого соединения драйвера, в том числе после переподключения.
Пути с пробелами, Unicode и `#` корректно кодируются в URI. Если существующая БД
уже больше заданного лимита, сервер останавливается с сообщением. Файл не удаляется
и автоматически не сокращается. Увеличьте лимит либо выполните обслуживание
проверенной копии БД, предварительно сохранив оригинал и резервные копии.

При достижении лимита запись, требующая новых страниц, завершается `SQLITE_FULL`.
API возвращает HTTP 507 с указанием лимита или нехватки места. Уже записанные
транзакции сохраняются. Очистка истории может освобождать страницы для повторного
использования без уменьшения размера файла. Некоторые операции чтения и удаления
продолжат работать, но авторизация, загрузки, мониторинг и журналирование могут
требовать новых записей: не используйте лимит как штатный режим эксплуатации.

Лимит основной БД **не является лимитом всего каталога runtime**. Дополнительное
место требуется WAL, файлам SHM, резервным копиям и временным операциям SQLite.
`journal_size_limit=16 МиБ` сокращает удерживаемый журнал после подходящего
checkpoint, но не ограничивает пиковый WAL при активной транзакции или читателе.
Существуют автоматические checkpoints и ежеминутный PASSIVE checkpoint.
Для резервирования требуется место ещё под согласованную копию основной БД;
ротация выполняется после успешного создания новой копии.

Проверено: заполнение тестовой БД до лимита, отказ следующей записи, `quick_check`,
освобождение/повторное использование страниц, повторное соединение, размер страниц
8192 байта, отказ слишком маленького лимита без потери существующих данных,
ответ API 507. Предупреждение до достижения лимита пока не реализовано.


## Восстановление при повреждении

При `SQLITE_CORRUPT`, `SQLITE_NOTADB` или ошибке целостности сервер ищет последнюю
пригодную копию в `storage.data/backups`. Порядок — от нового имени к старому
(штатные имена содержат UTC-время). Копии проверяются через `integrity_check`,
`foreign_key_check`, версию схемы и наличие администратора; повреждённые,
несовместимые и превышающие `database.max_mb` пропускаются. Проверяется отдельный
файл без WAL: подходят штатные согласованные копии `VACUUM INTO`.

В каталоге `storage.data/database-recovery-*` сохраняются:

- `original.sqlite3`, имеющиеся `original.sqlite3-wal` и `original.sqlite3-shm` —
  исходная повреждённая БД и журналы;
- `backup.sqlite3` — неизменённая выбранная резервная копия с исходными метаданными;
- при прерванном обмене — возможный `candidate.sqlite3`.

Автоматически эти архивы не удаляются. При нехватке места восстановление может
завершиться ошибкой. Если пригодной копии нет, сервер останавливается, сохраняя
исходную БД. Ошибки доступа, блокировки, заполнения и новая версия схемы сами по
себе не запускают восстановление. Файлы общей папки резервной копией БД не покрываются.

После восстановления сервер **не открывает порт**. Маркер
`lanbridge-go.sqlite3.recovery.json` блокирует обычный запуск. Прежде чем продолжить,
проверьте происхождение копии и учтите, что пользователи, пароли, роли, настройки
и история возвращаются к её дате. Потерянные после копирования изменения БД
автоматически восстановить нельзя. Сохраняйте архив для дальнейшего разбора.

В восстановленной БД автоматически:

- удаляются сессии и отзываются все гостевые ссылки;
- файловые ACL заменяются доступом только для администраторов;
- отключаются каналы уведомлений и внешний heartbeat, отменяется старая очередь;
- удаляются старые задания копирования/переноса, загрузок, индекс и записи корзины,
  чтобы они не повторили операции над нынешними файлами. Сами файлы, включая
  `.lanbridge` с корзиной и частичными загрузками, не удаляются. Разбирать их нужно
  вручную по метаданным сохранённой `backup.sqlite3`; они больше не видны в штатной
  корзине/очереди. Индекс обычных файлов строится заново, прежнее владение теряется.

Подтверждение запуска для локальной проверки (Windows, из корня проекта):

```powershell
.\dist\lanbridge.exe -config config.go.yaml -accept-database-recovery
```

Этот запуск принудительно слушает `127.0.0.1` и снимает маркер. Войдите с паролем
из копии, проверьте список администраторов/пользователей, смените устаревшие пароли,
заново задайте нужные ACL и проверьте мониторинг. Каналы включайте после проверки
получателей. На следующем обычном запуске используется адрес из конфигурации.
Не храните флаг подтверждения в постоянном скрипте/службе.

Если маркер содержит `ready: false`, обмен файлами прервался: даже флаг подтверждения
не откроет сервер. Остановите все экземпляры, сохраните весь runtime и сопоставьте
основную БД, её WAL/SHM и архив. Не удаляйте маркер вслепую и не смешивайте журналы
от разных БД. Для ручного восстановления используйте проверенную отдельную копию
и повторите проверку прав; исходные файлы сохраните для диагностики.

Проверено локально на Windows: пропуск испорченной новой копии, восстановление из
предыдущей, побайтовая сохранность повреждённого оригинала и выбранной копии,
отзыв сессии, повторный вход, принудительный loopback, блокировка повторного запуска,
недопустимая версия копии и маркер прерванного обмена. Сбой питания во время обмена
на физическом накопителе не моделировался; журнал защищает от продолжения неполного
обмена, но не заменяет внешнюю резервную копию.

```powershell
.venv\Scripts\python.exe scripts/verify_go_recovery.py
```
