# Журнал аудита Go-версии

Администратор открывает «Настройки → Журнал аудита». Данные загружаются только при
раскрытии раздела. По 50 событий на страницу, новые первыми; кнопки «Старее» и
«Новее» заменяют текущую страницу, не накапливая строки в DOM. «Обновить журнал»
возвращает к новым событиям. Фильтры применяются кнопкой: тип события и ID пользователя.
Обновления в фоне нет. Время отображается в часовом поясе браузера.

API: `GET /api/audit?limit=50&before=123&action=file_access&user_id=1`.
Все фильтры необязательны; `limit` — 1–100. `before` — ID предыдущей нижней строки,
а не номер страницы. Ответ содержит `items`, `has_more`, `next_before`.
Вставка новых событий не сдвигает уже просмотренные старые страницы. Для новых
событий используйте обновление. Запрос ограничен тремя секундами. Доступен только
администратору, через гостевой шлюз не публикуется.

## Что записывается

- Создание администратора, успешный/неуспешный вход; для входа — адрес соединения.
- Создание пользователя, изменение его пароля или роли (ID без пароля).
- Настройки оформления, проверки/массовые действия мониторинга, сканирование сети.
- Настройки каналов и наблюдателя; создание/отзыв ссылки (ID без токена).
- Включение/выключение внешнего доступа, восстановление БД.
- Файловые права (режим и относительный путь), квоты и сроки очистки хранилища.

Файловые пути, имена пользователей и IP являются частью журнала: доступ к БД и её
копиям ограничивайте администраторами. Пароли, токены гостевых ссылок и значения
секретных переменных окружения в новые записи не включаются. Текст деталей
отображается как текст, без исполнения HTML. Имя пользователя определяется по
текущей таблице пользователей; ID сохраняется отдельно.

Изменения файловых ACL и квот выполняются в одной транзакции с аудитом: отказ
записи журнала отменяет изменение. Такой же атомарный аудит есть для изменения
учётных записей, оформления и настроек мониторинга. Для остальных ранее
реализованных действий запись может выполняться отдельно после действия;
журнал не является криптографически защищённым или неизменяемым. Администратор
ОС может изменить саму БД. Скачивания/загрузки смотрите в истории передач.

Штатная очистка удаляет события старше 365 дней раз в минуту. Просмотр не меняет
срок хранения. Старые записи могут исчезнуть при переходе между страницами.
Экспорт и отдельная настройка срока хранения пока не реализованы.

Проверено: роли API, некорректные фильтры, курсорные страницы при новой вставке,
откат ACL/квот при отказе аудита, три страницы интерфейса на 120 записях,
экранирование HTML в деталях и мобильная ширина.

Изменение имени, значка и отметки «знакомое» устройства (`device_updated`), а также
настроек автопоиска (`discovery_config`) записывается атомарно с изменением БД.
При невозможности записать аудит изменение откатывается; отмена работающего
сканирования при отключении автопоиска выполняется только после успешного коммита.
В деталях записываются ID и новые параметры, без секретов. Обновление публикуется
в SSE для сводки устройств. Запуск сканирования остаётся отдельной операцией.

## Уведомления и заметки

Настройки канала (`notification_channel`) и внешнего наблюдателя
(`external_heartbeat`) сохраняются в одной транзакции с аудитом. Ошибка журнала
откатывает создание/изменение канала и включение/отключение наблюдателя.
Проверка лимита 16 каналов также выполняется в транзакции создания.

Запрос тестового сообщения (`notification_test`) и заметка к инциденту
(`incident_note`) теперь имеют атомарный аудит: при его отказе сообщение не попадает
в очередь, заметка не сохраняется. В журнале записывается только ID канала или
инцидента; текст заметки и секреты туда не копируются. Подтверждение постановки
в очередь не означает доставку внешнему адресату.

Регрессионные тесты принудительно запрещают INSERT аудита через SQLite-триггер:
проверены создание/изменение канала, наблюдатель, очередь тестового сообщения и
заметка. После снятия отказа операции снова проходят.
