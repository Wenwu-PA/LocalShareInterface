## Cloudflare Quick Tunnel

1. Установите `cloudflared` из [официального раздела загрузок](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/downloads/). На Windows выберите исполняемый файл своей архитектуры и разместите его в постоянной папке. На Linux используйте опубликованный Cloudflare пакет для своей ОС/архитектуры. Этот шаг не выполнен автоматически и в репозиторий бинарник не включён.
2. В `config.yaml` оставьте `tunnel.provider: cloudflare`; задайте `tunnel.cloudflared_binary` полным путём либо именем в PATH. Тот же параметр можно переопределить через `LANBRIDGE_CLOUDFLARED` в `.env`.
3. Оставьте `server.https: true`. Пустой `tunnel.origin_url` использует текущий порт; явный origin должен иметь схему HTTPS и адрес `127.0.0.1`, `localhost` или `::1`. Перезапустите LANBridge.
4. Создайте администратора до публикации. Откройте «Внешний доступ»: карточка провайдера должна показывать наличие `cloudflared`.
5. Включите переключатель. Приложение ожидает временный `trycloudflare.com` URL до 22 секунд. При отсутствии адреса останавливает дочерний процесс и возвращает ошибку; HTTP 200 ответа API ещё не означает успешное включение.
6. Откройте выданный URL с телефона через мобильную сеть и войдите. Для выдачи гостевой ссылки создавайте её в этой внешней вкладке: URL формируется из текущего origin. Гость получает доступ к выбранному объекту, но публичная страница входа приложения тоже остаётся доступной.
7. Выключите переключатель и повторите внешний запрос: адрес должен перестать обслуживаться. Штатная остановка LANBridge также завершает управляемый процесс. После перезапуска приложения туннель выключен.

Случайный адрес Quick Tunnel меняется при новом запуске, не требует собственного домена и не имеет гарантии непрерывной доступности. Этот режим предназначен для тестирования/разработки; ограничения и изменения провайдера смотрите в [официальной инструкции](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/). LANBridge не настраивает Cloudflare Access или email allowlist автоматически.

Самоподписанный сертификат локального origin принимается cloudflared без проверки издателя. Соединение браузер → Cloudflare и соединение cloudflared → origin — разные TLS-участки. Учитывайте доверие к Cloudflare и необходимость отдельной проверки origin в постоянной схеме.

## NetBird / существующая WireGuard-сеть

Включение `tunnel.provider: netbird` не подключает VPN: адаптер в этой версии возвращает ошибку. Для уже управляемой частной сети возможен самостоятельный доступ к LANBridge:

1. Установите клиент по инструкции [Windows](https://docs.netbird.io/get-started/install/windows) или [Linux](https://docs.netbird.io/get-started/install/linux); добавьте сервер и устройство получателя в свою существующую сеть. Чужие setup keys в `.env.example` не записывайте.
2. В управляющей панели VPN разрешите только нужным peers доступ к серверу и его TCP-порту. LANBridge не меняет VPN-политики и не устанавливает системные службы.
3. Привяжите сервер к доступному VPN-интерфейсу либо оставьте `0.0.0.0` и ограничьте интерфейсы firewall. Проверьте правила для профиля VPN-сети.
4. Используйте сертификат с VPN-именем/IP в SAN. Откройте HTTPS-адрес VPN-сервера и войдите обычной учётной записью LANBridge.
5. Для отключения удалите доступ peer в VPN-политике или отключите VPN-клиент. UI-переключатель LANBridge этого соединения не контролирует и не показывает его трафик как управляемый туннель.

Шаги предполагают существующую доверенную VPN-сеть; в данной среде они не выполнялись. Публичный IP для такого доступа приложению не нужен. Диапазон CGNAT принимается локальным фильтром, поэтому безопасность определяется также VPN ACL и firewall.

## Обратный прокси с доменом

Управление Nginx/Caddy/доменом из приложения не реализовано. `tunnel.provider: reverse_proxy` сообщает об этом вместо фиктивного включения. Для отдельного развёртывания администратору нужны такие действия:

1. Подготовить собственный домен, DNS, внешний TLS и proxy-сервер. Сертификаты и настройки относятся к инфраструктуре пользователя; готового публичного домена в проекте нет.
2. Обеспечить закрытый путь proxy → HTTPS-origin, правильный Host, передачу WebSocket Upgrade, потоковую обработку тела без полной буферизации и достаточные ограничения размера/таймаута.
3. Ограничить origin на firewall адресом proxy; настроить аутентификацию и rate limit на внешней границе. Не включать доверие к произвольным forwarded-заголовкам: LANBridge запускается с `proxy_headers=False`.
4. Проверить с внешнего клиента авторизацию, CSRF, Range, чанки, гостевые права и отзыв. Зафиксировать, какой IP видит приложение; если proxy скрывает клиента, его собственный аудит обязателен.
5. Для закрытия доступа остановить route/listener proxy и проверить внешний запрос. Переключатель LANBridge на независимый proxy не влияет.

Без этих проверок такая схема не считается поддержанной этим выпуском. Здесь намеренно нет непроверенного production-конфига под вымышленный домен. Управляемый lifecycle и корректная внешняя адресация этого адаптера входят в roadmap.

## NAT, CGNAT и проверка порта

Кнопка «Проверить сеть» получает внешний IP через `https://www.cloudflare.com/cdn-cgi/trace`. Только во время этой проверки запрос выходит на данный сервис. Частный адрес интерфейса говорит о локальной адресации, но не отличает домашний NAT от CGNAT провайдера.

Сравните внешний адрес с WAN IP в интерфейсе роутера. WAN из частного диапазона или `100.64.0.0/10` указывает, что прямой входящий доступ может быть недоступен. Туннель использует исходящее соединение и не требует проброса входящего порта LANBridge.

Приложение не запускает независимую пробу с внешнего узла и не доказывает доступность TCP-порта из интернета. Итоговая проверка выполняется с устройства вне LAN. Надпись о локальном порте не является результатом внешнего port scan.

## Если подключение не поднимается

- Проверьте путь и права запуска cloudflared, HTTPS origin и соответствие порта.
- Убедитесь, что firewall/DNS допускают исходящее подключение провайдера.
- Посмотрите сообщение в UI и операционный лог, удалив секреты перед передачей лога другому человеку.
- Не запускайте дополнительный cloudflared вручную для обхода ошибки UI: его остановка и аудит не будут управляться приложением.
- В Docker облачный бинарник не установлен; сначала подтвердите локальную работу контейнера и отдельно подготовьте управляемую интеграцию.
