# CPU и объём истории: 23 октября 2026

## Методика

Команда из корня проекта (Windows, установленное окружение с psutil):

```powershell
.venv\Scripts\python.exe scripts/compare_go_history_cpu.py
```

Два отдельных процесса RC одновременно работают по 600 секунд. У каждого своя
временная БД, 50 HTTP-мониторов с интервалом 20 секунд и локальная HTTP-цель.
Один цикл нагрузки — загрузка 8 МиБ, скачивание с проверкой SHA-256, пауза 5 секунд.
Измеряется CPU-время процесса сервера (user + system), включая мониторинг и
обслуживание БД; CPU на цикл — это всё время сервера, делённое на число таких
циклов передач. Это не стоимость одного SQL-запроса или одной проверки монитора.
CPU в процентах нормирован на одно логическое ядро.

Контрольная БД не содержит накопленной истории. Вторая получает 432000 сырых
измерений за 48 часов (50 мониторов, шаг 20 секунд) и 144000 минутных агрегатов.
Для заполнения оба тестовых сервера останавливаются, затем запускаются повторно.
После заполнения выполняется checkpoint; заполнение и начальная авторизация
исключены из CPU-замера. Запуск измерения синхронизирован по времени. Во время
замера работают обычные фоновые задания, включая очистку границы 48 часов.

Это одна парная проверка на общем компьютере: процессы конкурируют за ресурсы.
Она проверяет влияние истории мониторинга, но не воспроизводит накопленные
за сутки передачи, аудит, авторизации и внешнюю нагрузку компьютера. По одному
замеру нельзя устанавливать статистическую значимость или причину прошлого
скачка CPU.

## Исправление подготовки стенда

Первый замер завершил 600 секунд и 118 циклов на каждом сервере:
46,21 мс CPU/цикл (пустая БД) и 42,24 мс (48 часов). Однако история добавлялась
в работающую БД, поэтому два monitor batch получили `SQLITE_BUSY` во время
заполнения (08:30:04), до измерения (08:31:03). Этот вариант получил `FAIL`
из-за ошибок в журнале и не используется как окончательная приёмка.

Исправлен только тестовый стенд: массовая вставка выполняется при остановленном
сервере, после чего сервер запускается и авторизация проходит заново. Одинаковый
перезапуск выполняется и для пустой БД. Проверка отсутствия ошибок не ослаблена.
Предварительные артефакты сохранены в
[preliminary-empty](reports/cpu-history-2026-10-23/preliminary-empty/result.json) и
[preliminary-48h](reports/cpu-history-2026-10-23/preliminary-48h/result.json).

## План очистки агрегатов

`EXPLAIN QUERY PLAN DELETE FROM aggregates WHERE bucket<?` возвращает
`SCAN aggregates`. Это реальный проход по накопленным агрегатам раз в минуту.
Существующий индекс `aggregate_time(resolution,bucket)` используется при
выборке кандидатов компактации по разрешению; удаление сырых измерений использует
`samples_time(at)`. Планы сохранены в итоговых JSON. Сам факт полного прохода
не доказывает заметного влияния на общий CPU и не объясняет скачок в конце суток.

## Сроки хранения других таблиц

| Данные | Срок и очистка |
|---|---|
| `transfers` — история передач | Автоматического TTL и ограничения числа записей нет. |
| `audit` — аудит | Удаление записей старше 365 дней, обслуживание раз в минуту. Ограничения числа записей нет. |
| `notification_queue`, статус не `pending` | Старше 30 дней от `COALESCE(delivered_at, created_at)` удаляются; остаются не более 10000 последних записей по ID. |
| `notification_queue`, `pending` | TTL нет. Лимит 10000: старейшие сверх лимита получают `dropped` и затем подпадают под очистку завершённой истории. Это ограничение допускает потерю старых недоставленных уведомлений при переполнении. |
| `incidents` и `incident_events` | Автоматического TTL и ограничения количества нет, в том числе для закрытых инцидентов. Удаление монитора оставляет инцидент с `monitor_id=NULL`; события связаны с инцидентом через `ON DELETE CASCADE`. |

Очередь очищается при добавлении задания и обслуживании worker (не реже минуты
при работающем worker, также после попыток доставки). Удаление канала каскадно
удаляет его задания. Удаление строк не гарантирует уменьшения файла SQLite:
освобождённые страницы используются повторно.
