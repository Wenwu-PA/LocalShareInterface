# Суточная проверка релизного кандидата

Статус: 🕐 запускает пользователь. Короткий smoke не заменяет 24 часа.
Сценарий запускает отдельный сервер с временной БД, 50 HTTP-проверками раз в 20 с
и передачами по 8 МиБ. Рабочие данные и установленная служба не используются.
Проверка самой службы выполняется отдельно по [manual-checks.md](manual-checks.md).

## Windows

Из корня проекта, при наличии собранного `dist/lanbridge.exe`:

```powershell
python -m venv .venv-soak
.\.venv-soak\Scripts\python.exe -m pip install psutil
.\scripts\soak-24h.ps1 -Python .\.venv-soak\Scripts\python.exe
```

Если уже есть `.venv` с psutil, достаточно:

```powershell
.\scripts\soak-24h.ps1
```

Оставьте терминал открытым. Подключите питание и временно отключите автоматический
сон в настройках Windows. После завершения верните прежние настройки.
Скрипт сам не меняет питание. Блокировка экрана допускается; сон, перезагрузка
или выключение прерывают приёмку. Не пересобирайте используемый бинарник во время теста.

## Linux amd64

Перенесите проект и собранный `dist/lanbridge-linux-amd64` на Linux.
Из корня проекта (нужны Python 3 с venv/pip, Git и доступ для установки psutil):

```sh
python3 -m venv .venv-soak
.venv-soak/bin/python -m pip install psutil
chmod +x dist/lanbridge-linux-amd64
PYTHON="$PWD/.venv-soak/bin/python" sh scripts/soak-24h
```

Для другого бинарника передайте его путь первым аргументом `sh scripts/soak-24h`.
Оставьте сессию работающей 24 часа, запретите сон средствами своей ОС.
Linux-ветка подготовлена; фактический запуск на Linux требует подтверждения.

## Файлы и правило вердикта

В начале выводится поле `report` с каталогом `.verification/soak-<id>`.
Сохраните весь каталог. Каждые примерно 60 секунд (после текущей операции):

- `samples.csv`: время, число передач, RSS/Working Set, Private Bytes,
  CPU в процентах одного ядра за интервал, heap, горутины, размер основной БД и WAL;
- `samples.jsonl`: те же данные для машинной обработки;
- `result.json`: параметры, хеш бинарника, результат и оценка памяти;
- `server-tail.log`: последние строки журнала.

Все размеры в байтах. CSV содержит также начальный и конечный замеры.
Пропуск между замерами больше 120 секунд или длительная остановка нагрузки
не позволяет подтвердить непрерывный прогон. Ошибка запроса, хеша, монитора или
сервера означает FAIL независимо от памяти.

Для завершённых 24 часов сравниваются медианы RSS: **второй час** (3600–7200 с)
и **последний час**. Первый час — прогрев. В обоих окнах нужно не менее 30 точек.
Рост строго больше 20% выводит «Утечка есть по критерию роста RAM >20%» и FAIL
с кодом выхода 2. Иначе — «Утечки нет по критерию роста RAM >20%».
Это воспроизводимый критерий приёмки, не математическое доказательство отсутствия
любых утечек; рост кэша также может потребовать разбора. БД/WAL и горутины сохраняются
для диагностики, но рост БД от истории сам по себе не считается утечкой RAM.

Неполный/прерванный прогон выводит INCOMPLETE и не получает положительный вердикт
памяти. При внешнем убийстве тестового процесса отчёт может остаться RUNNING:
это тоже не успешный результат. Не объединяйте несколько коротких запусков в сутки.

При успехе пришлите `result.json`, `samples.csv`, `server-tail.log`, версию ОС,
время начала/конца и подтверждение отсутствия сна. При ошибке — те же файлы
и последние строки терминала; не отправляйте `.env.go`, пароли или ссылки с токенами.

## Проверка самого сценария

Выполнены тесты стабильной памяти, границы 20%, роста, прогрева, пропуска данных
и незавершённого запуска: `scripts/test_soak_memory.py`;
контроль непрерывности: `scripts/test_soak_continuity.py`.
`bash -n scripts/soak-24h` проверяет только синтаксис Linux-запускателя.
Windows smoke: `scripts/soak-24h.ps1 -Seconds 75`; это не суточная приёмка.
